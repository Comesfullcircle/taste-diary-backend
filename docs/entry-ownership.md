# 기록 소유권 연결

관련 이슈: [#7](https://github.com/Comesfullcircle/taste-diary-backend/issues/7)

## 목적

로그인 기능은 추가됐지만 기록 API는 아직 사용자 구분 없이 동작했다.
기록의 작성자를 저장하고 모든 접근을 본인 기록으로 제한했다.

## 접근 방식

- Controller에서 인증 객체의 이메일을 전달하고 Service에서 실제 회원 ID를 조회한다.
- 요청 DTO에는 작성자 필드를 두지 않아 클라이언트가 다른 회원을 작성자로 지정할 수 없다.
- 기록의 memberId는 생성 시 정하며 수정 메서드나 JPA 갱신 대상에 포함하지 않는다.
- 상세 조회·수정·삭제는 id와 memberId를 함께 조건으로 조회한다.
- 목록·검색에도 memberId 조건을 넣어 페이지 집계까지 본인 기록만 반영한다.
- 타인 기록과 없는 기록 모두 404로 처리해 기록 존재 여부를 구분하지 않는다.
- 회원을 DB에서 찾지 못하면 인증 오류로 처리하며 전체 기록 조회로 돌아가지 않는다.

회원 정보 자체가 필요한 도메인 동작은 없어 Entity에는 회원 ID만 저장했다.
DB 외래키로 유효한 회원을 참조하도록 보장한다.

## DB 변경과 기존 기록

V3 마이그레이션에서 필수 member_id와 members 테이블 외래키를 추가했다.
회원별 목록 조회를 위해 (member_id, experienced_on DESC, id DESC) 인덱스를 추가했다.

작업 전 로컬 DB의 기록 수가 0임을 확인했으므로 기존 기록을 배정할 필요는 없었다.
작성자가 없는 기록을 임의의 회원에게 배정하거나 삭제하지 않았다.
기존 기록이 있는 다른 환경에서는 이 마이그레이션이 실패하므로,
정당한 소유자 매핑을 먼저 결정하고 데이터 이전 계획을 세워야 한다.

## 인증과 CSRF

기록 API의 익명 접근 허용 설정을 제거했다.
로그인하지 않은 기록 요청은 CSRF 토큰 유무와 관계없이 401로 처리한다.
로그인한 회원의 변경 요청에서 CSRF 토큰이 없거나 잘못됐으면 403으로 처리한다.
가입·로그인·로그아웃의 CSRF 보호도 유지한다.

## 테스트

- 두 회원의 기록을 만들고 목록·검색·페이지 집계가 분리되는지 확인
- 다른 회원의 상세 조회·수정·삭제 요청이 404인지 확인
- 작성자 값을 임의로 전달해도 로그인 회원으로 저장되는지 확인
- 수정 요청으로 작성자를 변경할 수 없는지 확인
- 익명 요청의 401, 로그인 회원의 CSRF 오류 403 확인
- 실제 로그인 세션으로 기록 작성·조회 후 로그아웃 시 접근 차단 확인
- 기존 CRUD·검색·인증 테스트 확인

테스트에 @WithMockUser를 적용하는 과정에서 기존 CRUD 요청이 401로 실패했다.
Spring Boot 4의 보안 테스트 스타터로 변경한 뒤 테스트 인증 정보가 MockMvc 요청에 연결됐고
전체 테스트가 통과했다. 실제 세션 로그인 테스트도 함께 유지했다.

참고: [Spring Boot 4 보안 테스트 스타터 안내](https://github.com/spring-projects/spring-boot/wiki/Spring-Boot-4.0-Migration-Guide)
